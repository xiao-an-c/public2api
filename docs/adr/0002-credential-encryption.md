# 2. 凭据 AES-256-GCM 加密落库，密钥不可轮换

日期：2026-09-25
状态：已接受

## 背景

底子 `workbuddy2api-panel` 把凭据**明文**存在 JSON 文件里（`auths/` 一账号一文件）。
单渠道时这已经不好；多渠道路由之后风险会成倍放大——同一个库里会同时躺着
WorkBuddy 国内、国际、Grok 三条链路的凭据，其中 Grok 的 SSO cookie 是
「谁拿到它谁就等于拿到这个号」的形态。

来源仓库 `grok2api` 已经有现成实现：`internal/infra/security/cipher.go:18-46`，
AES-256-GCM，密钥是 Base64 编码的 32 字节。它的密文格式是 `base64(nonce ‖ seal)`。

## 决策

**凭据加密后落库**，直接移植 `grok2api` 的 cipher 实现。

**密钥首次写入账号后不可更换。** 密文里**没有密钥版本号、没有 KID 字段**——
nonce 是随机的，密文不自描述用哪把密钥。换密钥等于已有凭据不可逆丢失。

因此密钥的存放与备份必须在**写入第一个账号之前**定好。

**明文只存在于适配器发请求前的短暂窗口。** `adapter.Credential` 的 `String` 与
`GoString` 都改写为 `Credential{kind:..., fields:N}`，防止被 `fmt` 顺手打进日志。

## 后果

**好处**：数据库文件或备份泄漏不再等于账号全部失守；日志里不会出现凭据明文。

**代价与约束**：
- 密钥丢失 = 所有凭据不可恢复，只能重新接入每一个账号。密钥要单独备份，
  且**不能**和数据库放在同一个卷里。
- 无法做密钥轮换，也无法做「渐进式迁移到新密钥」。这是接受这个设计的直接代价。
- 底子的明文 `auths/*.json` 迁移时**保留不动**（只读、备份后不删），
  这样任何时候都能退回旧版本运行。

**为什么不用可轮换的方案**（密文头部带 KID、多密钥并存）：那是更正确的长期设计，
但它要求密钥管理（谁持有哪把、什么时候轮换、轮换后旧密钥留多久），
而这套东西目前没有运维载体。先接受一个简单且明确的约束，把复杂度留给真正需要时。

**未决**：密钥从哪来（配置文件字段 / 环境变量 / 外部 KMS）尚未定。
参考 `grok2api` 的做法是只读挂载的 `config.yaml`，且**没有**环境变量覆盖入口
（它唯一显式支持的环境变量是数据库 URL）。本仓库在实现阶段需要明确这一点，
并在 `AGENTS.md` 的硬约束里更新为确定的答案。
